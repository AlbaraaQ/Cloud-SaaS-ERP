# 06 — القرارات المعمارية (Decisions)

## D1 — خلفية واحدة بلا تجزئة

**القرار**: كل الأسطح على `apps/api` نفسه؛ لا API لكل سطح.
**السبب**: المواصفة صريحة (single shared backend)، والتجزئة كانت ستضاعف عقود المصادقة والعزل بلا عائد.
**الاستثناء الوحيد**: عمّال BullMQ خارج عملية الـ API (`WORKER=1`).

## D2 — الفصل بالنشر لا بالمستودعات

**القرار**: أربعة تطبيقات Next.js في نفس الـ monorepo، كل واحد ينشر وحده على نطاقه.
**السبب**: فصل حقيقي وقت التشغيل (عزل الجلسات والكوكيز والمصادقة) مع إبقاء الأدوات والـ CI موحدة.
**البديل المرفوض**: monorepo لكل سطح — تكلفة مزامنة العقود أعلى من فائدتها.

## D3 — `is_platform_admin` إشارة محسوبة لا مصدر حقيقة

**القرار**: أُبقي العمود للتوافق، لكن المرجع هو `platform_memberships` والرمز `pam`.
**السبب**: إسقاط العمود فوراً كان سيكسر أي عميل قديم يقرأ `/me`؛ الاشتقاق من العضويات يبقي السلوك صحيحاً أثناء التحول.

## D4 — الأسماء المستعارة للصلاحيات بدل القطع الفوري

**القرار**: `tenant.*` قياسي + `platform.*` مستعار في `@erp/contracts`، و`can()` ثنائي الاتجاه.
**السبب**: نفس منطق D3 — النشر التدريجي يتطلب عمل الواجهات القديمة والجديدة معاً. تُسقَط المستعارات في إصدار لاحق موثق.

## D5 — نسخ الملفات الصغيرة بدل حزمة مشتركة للواجهات

**القرار**: `api.ts` و`screen.tsx` و`card.tsx` ونحوها نُسخت بين التطبيقات (6–10 ملفات) بدل `@erp/ui`.
**السبب**: حزمة UI مشتركة كانت ستُدخل تبعية نشر متقاطعة بين الأسطح — عكس هدف الاستقلال. النسخ صريح وموثق في `04-migration-plan.md` وتكلفته أقل من الحوكمة.

## D6 — الكشف السلوكي لنوع الحساب في الدخول الذكي

**القرار**: `/me` مقابل `/portal/me` بدل حقل نوع في طلب الدخول.
**السبب**: لا نريد تسريب "هل هذا البريد موظف أم مشترٍ" قبل المصادقة (تعداد حسابات)، والكشف بعد المصادقة يستخدم قدرات الرمز الفعلية لا ادعاء المستخدم.

## D7 — جسر الرمز عبر الرابط مع التجريد الفوري

**القرار**: `?token=` يُستهلك عند الوصول ثم يُحذف من الشريط (`history.replaceState` / إعادة تحميل نظيفة).
**السبب**: البديل (إعادة كتابة بيانات الدخول) تجربة سيئة؛ والبديل الآخر (كوكيز مشتركة عبر النطاقات) مستحيل تقنياً على نطاقات منفصلة. النافذة الزمنية للرمز في الشريط لحظية فقط.

## D8 — طلب التفعيل للمصادق عليهم فقط

**القرار**: حُذف زر التفعيل المجهول من الأسعار العامة، وأُضيفت اللوحة لشاشة الترخيص.
**السبب**: الـ API يتطلب سياق منشأة (`tenant_id` من الجلسة) — الطلب المجهول مستحيل تصميماً لا إهمالاً. الصفحة العامة تُظهر الباقات وتوجّه للاشتراك أو للوحة الإدارة.

## D9 — التواصل عبر `mailto` قابل للضبط

**القرار**: صفحة تواصل حقيقية تُنشئ رسالة بريدية بدل نموذج ميت.
**السبب**: لا يوجد API رسائل في الخلفية، وبناء نظام تذاكر خارج النطاق. `NEXT_PUBLIC_SUPPORT_EMAIL` يجعلها صالحة لكل نشر.

## D10 — MFA يُكمل في سطح الموظفين

**القرار**: الدخول الذكي يوجّه حسابات TOTP إلى `staff` بدل تنفيذ خطوة ثانية فيه.
**السبب**: خطوة المصادقة الثانية حساسة أمنياً ولا تُنفَّذ في صفحتين؛ سطح واحد يملكها (staff) والآخر (platform-admin) يملك نسخته للمشغّلين.

## D11 — سجل القرارات المرفوضة

| المرفوض | السبب |
|---|---|
| صلاحية `*` للمنصة | تكسر D-العزل؛ كل دور منصة صلاحياته مسماة |
| `tenant_owner` يرى المنشآت الأخرى | مخالف للمواصفة؛ العزل مُختبَر |
| حذف `platform.*` فوراً | كسر توافق؛ استُبدل بالمستعارات (D4) |
| `@erp/ui` مشتركة | تبعية نشر متقاطعة؛ استُبدلت بالنسخ (D5) |
| صفحة تدقيق واحدة للسطحين | اختلاف النطاق (منشأة مقابل منصة)؛ صفحتان بمصدر واحد |
