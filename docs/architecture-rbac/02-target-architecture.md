# 02 — البنية المستهدفة (Target Architecture)

## 1. القواعد الحاكمة

1. **خلفية واحدة + قاعدة بيانات واحدة**: كل الأسطح تستهلك `apps/api` نفسه. لا Microservices لكل سطح. الاستثناء الوحيد: عمّال BullMQ (`WORKER=1`).
2. **فصل الأسطح نشراً لا كوداً خلفياً**: أربعة تطبيقات Next.js تنشر على نطاقات مستقلة، كلها على نفس الـ API.
3. **لا `*` لمنصة**: لا صلاحية عامة تمنح شيئاً خارج نطاقها. `tenant_owner` يتحكم بمنشأته فقط.
4. **لا حذف لوظيفة دون بديل موثق**، ولا واجهة صورية دون API حقيقي.
5. **كل تغيير قاعدة بيانات عبر ترحيل آمن بلا فقدان** (`packages/database`).

## 2. الأسطح الأربعة

| التطبيق | الحزمة | النطاق | المنفذ | الوظيفة |
|---|---|---|---|---|
| `apps/marketing` | `@erp/marketing` | `yourdomain.com` | 3002 | موقع عام: رئيسية/أسعار/تواصل/تحقق/تهيئة + دخول ذكي |
| `apps/staff` | `@erp/staff` | `app.*` | 3001 | إدارة المنشأة + كل ERP |
| `apps/platform-admin` | `@erp/platform-admin` | `platform.*` | 3003 | لوحة مشغّلي المنصة |
| `apps/customer-portal` | `@erp/customer-portal` | `portal.*` | 3004 | بوابة المشترين الذاتية |
| `apps/api` | `@erp/api` | `api.*` | 3000 | الخلفية المشتركة الوحيدة |

## 3. RBAC المستهدف

- **Family A — أدوار المنصة** (`platform_roles` + `platform_memberships`): `platform_owner`، `platform_operations`، `platform_billing`، `platform_support`، `platform_auditor`. المنح/السحب عبر `POST/DELETE /platform/users/:id/roles`، والواجهة في `/roles` بلوحة المنصة.
- **التوافق**: `users.is_platform_admin` بقي كإشارة محسوبة (legacy) تُشتق من العضويات الفعلية؛ الرمز `pam` في الجلسة هو المرجع.
- **أذونات المنشأة**: نطاق `tenant.*` القياسي (`tenant.profile.view`، `tenant.users.manage`…) مع أسماء مستعارة للخلف (`platform.*` القديمة) في `@erp/contracts`، و`can()` في الواجهات يفهم الاتجاهين.
- **`memberships.kind`**: `staff` | `buyer` | `api` — يفصل الموظف عن المشتري عن التكاملات.
- **الأجهزة**: كيان `devices` مستقل بسجل خاص (`/devices`) بدل ربطه بالمستخدم/الكاشير.

## 4. التنقل بين الأسطح

- الدخول الذكي (`marketing/login`): يصادق مرة واحدة ثم يكتشف نوع الحساب سلوكياً (`/me` مقابل `/portal/me`) ويوجّه للسطح الصحيح.
- جسر الجلسة (`?token=&refresh=&tenant=`): يستهلكه `TokenBridge` في `staff`/`customer-portal` ثم يُجرَّد من الشريط — لا إعادة كتابة لبيانات الدخول.
- روابط الأسطح عبر `NEXT_PUBLIC_{STAFF,PORTAL,PLATFORM,MARKETING}_URL` — لا روابط ثابتة بين النطاقات.

## 5. ما لم يتغير عمداً

- عقود الـ API العامة: كل المسارات القديمة تعمل (الأسماء المستعارة + الاستجابات نفسها).
- سلوك الفوترة والاشتراكات: نُقلت الواجهات فقط، المنطق كما هو.
- قاعدة البيانات: إضافات فقط (جداول/أعمدة جديدة)، لا حذف أعمدة مستخدمة.
