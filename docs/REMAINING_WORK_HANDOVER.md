## 1. تهيئة البيئة من الصفر (ترتيب دقيق)

```bash
corepack enable && corepack prepare pnpm@9.15.0 --activate
pnpm install --no-frozen-lockfile
pnpm env:setup          # يولّد .env الجذر بمفاتيح RSA وكلمات مرور جديدة — أعد البذر بعده
pnpm -r --filter "./packages/*" build   # إلزامي قبل أي أمر يعتمد على الحزم
pnpm db:local           # PostgreSQL مضمّن (لا يوجد docker/psql في هذه البيئة)
pnpm db:migrate         # حتى 0031
pnpm db:seed
pnpm dev                # API :3000 · لوحة التحكم :3001 · بوابة العملاء :3002
```

- **لا تحاول تثبيت Docker أو Postgres** في بيئة العمل — الكود يُكتب ويُختبر على
  `pnpm db:local`، والتشغيل الحقيقي عند المستخدم عبر `infrastructure/docker-compose.yml`.
- الخلفية: استخدم أدوات العمليات (`start_process`) للخوادم، لا `nohup`. سجّل الـ API في
  `/tmp/api.log` عبر `node apps/api/scripts/dev.mjs > /tmp/api.log 2>&1`.
- **لا تشغّل `next build` وخادم Next يعمل** (تعارض معروف؛ التعافي بحذف `.next`).
- الحسابات: `owner@demo.test` / `demo`، كلمة المرور في `.env`. الواجهة بالعربية والتواصل بالعربية.

## 3. البنود المتبقية (مرتبة بالأولوية المقترحة)

### 3.1 الفوترة الإلكترونية — توقيع XAdES واعتماد ZATCA 🔴

الوثائق الحية: `apps/api/src/modules/einvoicing/README.md` (يشرح بالضبط ما المنجز وما المتبقي).

- **المنجز:** مستند UBL 2.1 حقيقي، سلسلة تجزئة + عدّاد (ترحيل `0029`)، توقيع ECDSA عند توفر
  المفتاح، رمز QR بالوسوم 1–5 من بيانات المنشأة.
- **المتبقي:**
  1. كتلة توقيع **XAdES** داخل `UBLExtensions` (الوسوم 6–8 في QR تصبح حقيقية).
  2. مسار الاعتماد: توليد CSR على قالب ZATCA، استدعاء CSID الامتثال، فحوصات الامتثال،
     ثم استبدال CSID الإنتاجي. اليوم يقوم بها العميل يدوياً وتُخزن النتائج في
     `PUT /einvoice/credentials`.
- **المدخل:** `apps/api/src/modules/einvoicing/zatca/{ubl,qr}.ts` و`einvoicing.service.ts`.
  مكتبات مرشحة: `node-xmldsig`/`xml-crypto` للتوقيع، أو بناء XAdES يدوياً على `node:crypto`.
- **قبول:** اختبار وحدة يثبت صحة بنية `UBLExtensions`، واختبار تكامل يحول حالة التقديم إلى
  `signed` بمفتاح مرفوع. الاعتماد الفعلي على بيئة ZATCA التجريبية يتطلب شبكة خارجية — وثّقه
  كخطوة يدوية بدل محاولة أتمتته هنا.

### 3.2 محدّد المعدل في الذاكرة 🟠

`apps/api/src/modules/platform/rate-limit/rate-limiter.service.ts` يعمل في ذاكرة العملية —
لا يحمي عند تعدد النسخ.

- **المدخل:** حوّله إلى Redis (الخدمة موجودة في `docker-compose` على `:6379`) مع تراجع تلقائي
  إلى الذاكرة عندما لا يتوفر `REDIS_URL`. المتغير في `packages/config/src/env.ts`.
- **قبول:** اختباران — نافذة مشتركة بين نسختين (محاكاة بمخزن مشترك)، وتراجع سليم بلا Redis.

### 3.3 النسخ الاحتياطي خارج قاعدة البيانات 🟠

اليوم النسخ لقطات جدولية داخل قاعدة البيانات نفسها (انظر `app/settings/backup/page.tsx`
و`/settings/backups`) — وهذا لا يصمد أمام فقدان القرص.

- **المدخل:** أضف موجّه تخزين يستهدف MinIO (منفذ التخزين الكائني `OBJECT_STORAGE` موجود أصلاً في
  `platform-services/files/object-storage.ts`) أو مسار ملفات محلي، مع تشفير وجدولة عبر طابور
  المهام (`jobs/`).
- **قبول:** نسخة قابلة للتنزيل والاستعادة من `0031` فصاعداً، واختبار تكامل واحد على الأقل.

### 3.4 مزامنة سلة تلقائية بدل الإدخال اليدوي 🟡

التكامل الحالي (`apps/api/src/modules/integrations/salla/`) يعتمد إدخال مفاتيح المتجر يدوياً.

- **المدخل:** تدفق OAuth/توكن المتجر + سحب المنتجات والطلبات عبر Webhooks
  (`/integrations/salla/webhooks/:storeId/orders` موجود كهيكل) مع طابور مهام للمزامنة الدورية.
- **قبول:** إعداد متجر واحد يجلب منتجاته وطلباته دون إدخال يدوي، مع تسجيل الأخطاء في سجل المزامنة.

### 3.5 اختبارات E2E للواجهة 🟡

لا توجد اختبارات متصفح. التحدي البيئي: تنزيل متصفحات Playwright يتطلب شبكة وقد لا يتوفر.

- **المدخل المقترح:** `@playwright/test` في مجلد جديد `e2e/` يغطي: الدخول → شاشة محاسبة →
  إنشاء فاتورة → طباعة؛ ومنح وصول بوابة → دخول العميل على `:3002`.
- **قبول:** سير عمل واحد ناجح لكل تطبيق (لوحة التحكم، بوابة العملاء) يعمل بـ `pnpm e2e`.

### 3.6 استكمال شاشة اللغة على مستوى محتوى الشاشات 🟢

الهيكل مكتمل (`lib/i18n.tsx`، شاشة `/settings/language`، القوائم وشاشة الدخول مترجمة).
محتوى الشاشات نفسها بقي عربياً أولاً بقرار موثق.

- **المدخل:** مدّ قاموس `STRINGS` أو إضافة طبقة `t()` داخل الصفحات تدريجياً — ابدأ بالصفحات
  الأكثر استخداماً (الرئيسية، الفواتير، السندات).
- **قبول:** أي صفحة تُترجم يجب أن تظهر بالإنجليزية كاملة عند اختيار English (اختبار بصري).

## 4. قيود ثابتة من المستخدم (لا تُخالف)

1. التواصل بالعربية، والواجهة عربية أولاً (الإنجليزية خيار إضافي).
2. وحدة تحكم المنصة داخل `apps/admin` في `/platform` — لا تطبيق منفصل.
3. لا تثبيت Docker/Postgres في بيئة العمل؛ التوثيق للمستخدم عبر `docker compose`.
4. الواجهة تطابق شجرة النظام المكتبي (الوحدات الثمانية + الدعم الفني).
5. لا حذف ولا إعادة تسمية لجذر المستودع أو `.git`؛ العمل والدفعات على
   `arena/01a07f00-cloud-saas-erp` فقط.

## 5. مطبّات معروفة (توفيراً للوقت)

- **سجل الأخطاء ثابت وقابل للتمديد فقط** (`packages/contracts/src/errors.ts`) — أضف في الذيل.
- إضافة قيمة لعمود حالة = تعديل قيد `CHECK` في ترحيل جديد (كما حدث مع `0029`).
- الخدمات تحقن `DATABASE_HANDLE` أبداً، لا `getDatabase()` مباشرة (وإلا فشلت العزلة في الاختبارات).
- `createTestApp('<slug>')` يعطي قاعدة مضمّنة جديدة لكل ملف اختبار؛ الممثل يحتاج صلاحيات مطابقة
  وإلا عاد 403 صامت. المستأجر الجديد بلا حسابات ولا أصناف ولا أطراف.
- الاختبارات التي تعتمد متغيرات بيئة بعد تحميل `@erp/config` يجب أن تقرأ من `process.env` مباشرة
  (انظر `live()` في `notifications/mailer.ts`) — الكائن المُحلَّل يُخزّن مرة واحدة لكل عامل.
- `vi.hoisted` لضبط البيئة قبل الاستيرادات في ملفات الاختبار.
- لا `git stash`؛ استرجاع التراجعات عبر `git fetch` ثم `reset --mixed FETCH_HEAD`.
- `pnpm --filter <pkg> lint -- --fix` لا يعمل — استخدم `npx eslint <paths> --config ../../eslint.config.mjs --fix`.
- لا يوجد `tsc` في جذر `node_modules` — استخدم `../../node_modules/.bin/tsc --noEmit -p tsconfig.json`
  من داخل التطبيق.
- حدود الواجهة: أعمدة `DataTable` من `components/data-view.tsx`؛ أخطاء `useQuery` نصية؛
  `FormFields.onChange` يستلم الكائن كاملاً؛ صفحات المسار الديناميكي `params` فيها Promise.
- حارس الأموال يمنع معرّفات مثل `price|amount|total|balance` وحدها (استخدم أسماء مركبة).
- ملفات صفحات Next لا تصدّر دوال مساعدة؛ `useSearchParams` يتطلب `Suspense`.
